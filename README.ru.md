Веб-чат для мессенджера MAX на [GREEN-API](https://green-api.com/max). Вы входите по данным
своего инстанса, открываете чат по номеру телефона, отправляете текстовые сообщения и видите
ответы, как только они приходят. Интерфейс повторяет [web.max.ru](https://web.max.ru): палитра
темы «space», пузыри, список чатов и мобильная раскладка.

Бэкенда у приложения нет. GREEN-API отвечает с `Access-Control-Allow-Origin: *`, браузер ходит
в API напрямую, и проект собирается в статические файлы.

## Запуск

```bash
npm install
npm run dev
```

Нужен Node 20.19+ или 22.12+. Откройте адрес, который выведет Vite, и войдите:

1. Создайте инстанс MAX в [личном кабинете GREEN-API](https://console.green-api.com). Хватит
   бесплатного тарифа Developer.
2. Авторизуйте его: в приложении MAX откройте «Профиль → Устройства → Войти по QR-коду» и
   отсканируйте код из кабинета.
3. Скопируйте `idInstance` и `apiTokenInstance`. Поле `apiUrl` можно оставить пустым:
   приложение строит адрес из первых четырёх цифр `idInstance`, например
   `https://3100.api.green-api.com`.

Чтобы не вводить ключи каждый раз, скопируйте `.env.example` в `.env` и заполните его.
Dev-сервер подставит значения в форму входа. В production-сборку они не попадают, это видно
поиском по `dist`. `npm run dev` запускает `vite --host` и отдаёт заполненную форму в
локальную сеть, поэтому держите настоящие ключи в `.env` только в сети, которой доверяете.

| Команда | Что делает |
|---|---|
| `npm run dev` | dev-сервер с горячей перезагрузкой |
| `npm test` | Vitest, 44 теста |
| `npm run build` | проверка типов и сборка в `dist` |
| `npm run preview` | отдаёт `dist` локально |
| `npm run lint` | oxlint |

## Как это устроено

```
  вкладка браузера                                GREEN-API (инстанс MAX)
  ----------------                                -----------------------
  форма входа ─── getStateInstance ─────────────▶ авторизован?
  сайдбар     ─── getSettings / setSettings ────▶ входящие включены?
              ─── getChats ─────────────────────▶ личные чаты
  новый чат   ─── checkAccount(телефон) ────────▶ числовой chatId
  открыть чат ─── getChatHistory(chatId, 100) ──▶ последние сообщения
  поле ввода  ─── sendMessage(chatId, текст) ───▶ idMessage
  цикл опроса ─── receiveNotification (20 с) ───▶ входящее сообщение
              ─── deleteNotification(receiptId) ▶ очередь идёт дальше
        │
        ▼
  редьюсер ──▶ localStorage ──▶ другие вкладки (событие storage)
```

| Файл | Отвечает за |
|---|---|
| `src/api/green-api.ts` | HTTP-запросы, тексты ошибок, `apiUrl` из `idInstance` |
| `src/lib/poll.ts` | цикл long polling, удаление каждого уведомления, повтор раз в 5 секунд |
| `src/lib/notification.ts` | разбор входящих уведомлений |
| `src/lib/history.ts` | разбор ответов `getChats` и `getChatHistory` |
| `src/lib/chat-state.ts` | редьюсер: чаты, сообщения, статус отправки, слияние истории |
| `src/lib/storage.ts` | localStorage, восстановление после битых данных |
| `src/lib/phone.ts` | нормализация номеров России и Беларуси |
| `src/hooks/useNotifications.ts` | одна опрашивающая вкладка на инстанс через Web Locks |
| `src/components/Messenger.tsx` | отправка, повтор, загрузка чатов и истории, синхронизация вкладок |
| `src/components/ReceivingNotice.tsx` | проверка настроек инстанса и кнопка «Включить» |

## Журнал решений

**chatId берётся из CheckAccount.** MAX различает собеседников по числовому `chatId`
(`"10000000"`), и входящие уведомления несут именно его, номера телефона в них нет. Чат,
открытый на `79991234567@c.us`, никогда не совпал бы с ответом. Поэтому новый чат сначала
вызывает `checkAccount`. Для номера, который уже есть в списке, приложение этот вызов
пропускает: тариф Developer даёт 100 проверок в месяц.

**Каждое уведомление удаляется.** Очередь HTTP API работает по FIFO. Уведомление о статусе или
медиа, оставленное в очереди, блокирует всё, что пришло после него, поэтому цикл удаляет все
уведомления, а в чат передаёт только текст. Сообщение попадает в редьюсер до удаления
уведомления. Если удаление сорвётся, уведомление придёт снова, и редьюсер отбросит его по
`idMessage`.

**Проверка настроек появилась после живого прогона.** На настоящем инстансе ответ не пришёл.
`getSettings` вернул `incomingWebhook: "no"`, и документация GREEN-API подтверждает: у нового
инстанса все уведомления выключены. Теперь приложение после входа читает настройки и
предлагает кнопку «Включить». Молча настройку оно не меняет: `setSettings` перезапускает
инстанс, изменение вступает в силу за пять минут. При заданном `webhookUrl` приложение только
объясняет ситуацию, потому что очистка поля сломала бы чужую интеграцию.

**Лимиты запросов в разработке.** React StrictMode в dev запускает эффекты дважды, и GREEN-API
ответил на второй `getSettings` кодом 429. Теперь проверка повторяет запрос до трёх раз с
паузой в две секунды.

**Очередь читает одна вкладка.** Две открытые вкладки забирали уведомления по очереди, ответ
появлялся только в одной из них, а вторая могла затереть его в localStorage. Теперь цикл опроса
работает внутри `navigator.locks.request`, остальные вкладки получают изменения через событие
`storage`, а выход в одной вкладке завершает сессию во всех.

**История грузится при открытии чата.** `getChats` отдаёт список одним запросом, но история
нескольких десятков чатов разом упёрлась бы в лимит запросов в секунду. Приложение загружает
последние 100 сообщений, когда вы открываете чат. После отправки локальное сообщение получает
`idMessage` из ответа, и та же запись из истории не задваивается. Приложение принимает этот id,
только если это непустая строка, иначе оставляет локальный.

**Ключи не попадают в сборку.** `vite.config.ts` открывает клиентскому коду ключи из `.env`
только при `command === 'serve'`. Production-сборка видит лишь переменные `VITE_`, и поиск
токена по `dist` ничего не находит.

**Локальные id без crypto.randomUUID.** С `vite --host` dev-сервер можно открыть с телефона по
обычному HTTP. В таком небезопасном контексте `crypto.randomUUID` нет, и отправка падала,
поэтому локальные id строятся из времени и `Math.random`.

**Прокрутка без JS.** Лента сообщений устроена как `flex-col-reverse`, и браузер сам держит её у
последнего сообщения. Список пересоздаётся для каждого чата (`key`), иначе он сохранял позицию
прокрутки предыдущего чата.

**Цвета.** Токены сняты с web.max.ru (тема «space»). Два из них не прошли проверку контраста
WCAG AA, поэтому красный цвет ошибок `#e0242f` вместо `#ff303c`, а вторичный текст в списке
чатов темнее. Иконки взяты из Phosphor, своих SVG в коде нет.

## Тесты

```bash
npm test
```

44 теста на Vitest проверяют запросы к API (URL, метод и тело для каждого эндпоинта), разбор
уведомлений и истории, редьюсер, восстановление после битых сохранённых данных и цикл опроса:
отмену во время запроса, отмену во время паузы и интервал повтора в пять секунд.

Ручная проверка в браузере, на мок-API и на настоящем инстансе: вход, включение уведомлений,
чат по номеру, отправка, ответ в том же чате.

## Деплой

`.github/workflows/deploy.yml` на каждый push в `main` ставит зависимости, запускает тесты,
собирает проект и публикует `dist` на GitHub Pages. В ветке `gh-pages` лежит та же сборка,
сделанная локально, на случай если Actions недоступны.

## Ограничения

- Только текстовые сообщения и личные чаты: без медиа, групп, реакций и отметок о прочтении.
- Номера России (+7) и Беларуси (+375): CheckAccount не принимает другие страны.
- Бесплатный тариф Developer даёт 3 чата и 100 вызовов CheckAccount в месяц.
- История охватывает последние 100 сообщений чата, GREEN-API хранит её три месяца.
- Сообщения, отправленные из приложения MAX на телефоне, появляются после повторного открытия чата.
- Данные входа лежат в localStorage вашего браузера, потому что сервера для их хранения нет.
